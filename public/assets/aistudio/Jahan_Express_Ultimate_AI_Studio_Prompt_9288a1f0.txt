Build a complete, polished, responsive, multi-page website for Jahan Express / Jahan Express Solution, an Indian logistics business. Deliver working implementation, not just a design description or homepage mockup.

Make the website feel premium, trustworthy and remarkably easy to use. Combine the calm clarity of Google's product experiences with strong logistics photography and purposeful business workflows. This should feel like a distinctive Jahan Express website, not a Google clone. A first-time visitor should quickly understand services, coverage, how to request a quote and how to get shipment support.

Use the attached desktop image as the main visual direction and the mobile sheet for responsive behavior. Recreate composition and quality using real HTML/CSS components, not a screenshot embedded as the website. Images are design references; do not reproduce invented logos, implied operational claims or unverified captions from them.

VISUAL SYSTEM
- Bright white base #FFFFFF; alternating soft backgrounds #F8FAFD and #EEF5FF.
- Primary blue #1A73E8, darker accessible hover shade; charcoal #17212F; secondary text #5F6B7A; fine borders #E3E8EF. Check final contrast rather than assuming every combination passes.
- Use one consistent readable sans-serif, such as Inter, with system fallback. Do not rely on proprietary Google fonts.
- Desktop centered content width around 1200–1280px; comfortable 24–40px gutters; generous 80–112px section spacing. Scale spacing naturally on mobile.
- Fluid hero headings around 48–68px desktop and 34–42px mobile; body around 16–18px; line height around 1.5–1.7.
- Restrained 16–24px card radii, crisp borders, low-elevation shadows and consistent 48px minimum primary control height.
- Use one coherent outline icon family. Real service photography, clean crops and balanced whitespace should carry the visual identity.
- Desktop sticky header: brand, Home, About, Services menu, Coverage, Contact, prominent Get a quote CTA. Tracking must remain easy to find.
- Mobile: accessible collapsible navigation, stacked content, useful thumb-sized actions. Keep copy and inputs readable without zooming.
- Motion should be subtle: 150–250ms feedback, gentle reveals only where helpful, with reduced-motion support. No autoplay hero carousel or decorative cursor effects.
- Avoid neon, excessive glass effects, purple gradients, spinning globes, stock-template clutter and giant empty hero areas.

INNER PAGE UX
About: company story, accurate dates, mission, vision, values, approach and contact CTA. Do not invent team members or portraits.
Services overview: four service cards with easy comparison of suitable shipment needs. Do not imply unverified transit times or fixed prices.
Service detail: breadcrumb, distinct headline and photo, who it helps, shipment examples, process, availability conditions, relevant FAQs and preselected quote CTA.
Student Express: warm, student-friendly presentation; books, instruments and belongings; home/hostel directions; request student pricing without inventing discount percentages.
Coverage: searchable region/destination list drawn from confirmed data, special-zone information, manual availability enquiry when no live PIN database exists. Do not mark all Indian PIN codes serviceable.
Contact: clean contact cards, distinct registered/work addresses once confirmed, office hours, working call/email links and accessible enquiry form. Use a configurable map link/embed only after the address is verified.
FAQ: practical answers on choosing a service, requesting quotes, packing, pickup coordination, special destinations and tracking support. State that exact transit times, pricing, accepted goods and conditions require confirmation.

WORKING QUOTE FLOW
Implement a responsive three-step flow: Shipment → Contact → Review.
Shipment: service, domestic/international where relevant, origin/destination country and locality, Indian PIN fields when applicable, package count, total weight in kg, optional dimensions in cm, preferred pickup date and cargo description.
Contact: full name, phone, email and business name optional. Explain why contact details are needed.
Review: readable summary, edit links and submit action. Preserve values when moving back. Preselect the service from service-detail CTAs.
Validate required fields, six-digit Indian PINs only for Indian addresses, phone/email formats, positive dimensions/weight/count and sensible dates. Do not force international postcodes into Indian PIN format.
Use inline errors and focus the first invalid field. Provide loading, failure, retry and success states. Show success only after a real configured endpoint accepts the enquiry. In demo mode, say “Demo request — not sent” and offer an editable enquiry summary with a clear email option; opening an email app is not successful submission.
Do not invent automatic prices, confirmed bookings, payment processing or pickup guarantees.

TRACKING
Create a proper adapter interface for a future shipment API, with demo and live implementations. Default to explicitly labelled demo mode if no integration is configured. Provide a visible sample tracking ID and a sample timeline that is unmistakably illustrative. Real arbitrary IDs must never generate fabricated shipment progress.
Support empty/invalid input, loading, found, not found, unavailable and network error states. Include last-updated time and a clear timeline only when data supports them. Do not promise GPS tracking or expose customer addresses publicly. Future production access must use an appropriately protected server integration; never put carrier secrets in frontend code.

OPTIONAL ASSISTANT
Only after the core site is complete, add a compact help panel that can guide users to services, quote requests, contact and tracking support. A useful deterministic help flow is sufficient. Do not pretend it is an AI model. If a real model is configured, keep credentials server-side and ground answers in approved company content; the assistant must not invent rates, statuses or commitments. Keep it unobtrusive on small screens.

IMPLEMENTATION
Use the build environment's supported React + TypeScript setup, reusable components and a consistent styling system, preferably Tailwind CSS if available. Use proper routing with direct route loading and browser navigation. Do not force unsupported dependencies. Keep company information, services, coverage and feature flags in typed configuration. Separate page presentation from enquiry, tracking and optional assistant integrations.
Provide sensible image fallbacks, error boundaries and clear empty states. No dead buttons, placeholder links, lorem ipsum or console errors. Do not put private keys or personal enquiry data in source code, URLs or analytics logs. Do not persist contact details in localStorage by default. For production enquiry endpoints, specify server validation and abuse prevention; do not claim backend features are live without implementing/configuring them.

ACCESSIBILITY / PERFORMANCE / SEARCH
Use semantic landmarks, logical headings, visible keyboard focus, persistent field labels, aria-expanded on accordions/menus, correct dialog focus management and accessible error announcements. Aim for WCAG 2.2 AA and verify contrast and keyboard behavior. Respect reduced motion.
Optimize images, reserve layout space, lazy-load below-fold assets and keep the main hero image appropriately prioritized. Avoid unnecessary large animation packages. Aim for good Core Web Vitals; report measured results only if actually tested.
Add unique page titles/descriptions, canonical URLs based on actual production deployment, Open Graph metadata, sitemap and robots configuration. Use accurate Organization/LocalBusiness structured data only from approved details, with no fabricated ratings. Draft policy pages and demo-only views should not be accidentally presented as finalized legal/operational content.

DELIVERY AND ACCEPTANCE
Work in this sequence internally: inspect source/reference images → outline content mapping and unresolved facts → establish design tokens/components → implement all routes → implement interactions → verify responsive/accessibility behavior → deliver.
Do not stop after planning. Produce the working project in the build environment, then briefly explain completion and configuration needs.
Verify at roughly 360, 390, 768, 1024 and 1440px widths; no horizontal overflow. Check long headings, mobile menus, service links, quote back/next behavior, validation, keyboard navigation, FAQ toggles, tracking demo/error states, contact links and direct route loading.
Deliver:
- Complete source code, organized assets and dependency manifest.
- Setup/run/build instructions and environment-variable example without secrets.
- Content migration checklist covering all source material that was accessible.
- Honest list of demo features, integrations still required and unverified business details.
- Notes for old URL redirects, production deployment and replacing temporary assets.
The result should look composed and premium at first glance and remain useful through every page and interaction.
